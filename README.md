# SchoolFix AI — 학교 불편사항 신고 및 시설 안전 관리

학생이 학교별 교내 시설 문제를 신고하면, AI가 위험도를 채점하고, 누구나 처리 현황을 확인할 수 있는 **로그인 없는 공개형 웹 서비스**입니다.

"복도 타일이 들떠서 넘어질 뻔했다" 같은 제보가 종이나 구두로 흩어지지 않고, 접수번호와 위험도가 남는 기록으로 관리되는 것을 목표로 합니다.

---

## 무엇을 할 수 있나

로그인도 회원가입도 없습니다. 첫 접속에서 지원 학교를 고르면, 학교별 신고와 확인된 위치 카탈로그가 적용됩니다.

- **신고 등록** — 선택한 학교의 공식 확인 위치를 고르고, 공개되지 않은 건물·층·학과·학년·반·호실은 필요할 때 직접 입력합니다. 이름·학번·연락처는 **수집하지 않습니다.**
- **학교 지원** — 지원 학교는 학교 선택 화면에서 고릅니다. 학교 추가 신청은 웹 내부 신청함(운영진 메일함) 또는 `mailto:` 메일 초안으로 보낼 수 있고, 운영진이 메일함에서 승인하면 바로 지원 학교로 등록됩니다.
- **작성 도우미** — 상황별 예시 문구 10종을 제공해, 무엇을 어떻게 써야 할지 막막한 학생도 버튼 한 번으로 초안을 채웁니다.
- **AI 추가 질문** — 내용이 애매하면 바로 접수하지 않고, 가장 중요한 질문 **하나**를 되묻습니다. 답변을 합쳐 다시 판단하고, 충분해지면 그때 저장합니다.
- **내 신고 / 전체 신고** — 탭으로 구분해 조회합니다. 검색, 카테고리·위험도·처리 상태·기간 필터를 조합할 수 있습니다.
- **위치별 신고 현황** — 어느 장소에서 문제가 가장 많이 발생하는지 실제 신고 데이터로 집계합니다. 위의 필터가 그대로 반영됩니다.
- **AI 요약** — 접수된 신고 전체에서 드러나는 문제 상황을 간결하게 정리합니다.
- **PDF 저장 / 인쇄** — 현재 필터가 적용된 목록을 보고서 형태로 내보냅니다.
- **간편 신고 작성** — 작성 진행 표시, 문제 종류 바로 선택, 자주 쓰는 예시, 사진 끌어놓기와 현재 탭 임시저장을 제공합니다. 초안에는 글 내용만 저장되며 사진과 AI 추가 질문 답변은 저장하지 않습니다.

학교별 데이터는 서버 측 [`schools.seed.json`](./schools.seed.json) 카탈로그에서 제공합니다. 학교 현황에 나온 학과 및 학년별 학급 수는 참고 정보로 저장하고, 실제 반 이름·건물명·층·호실은 공식 공개 자료에 없어 선택 목록으로 만들지 않고 신고자가 직접 적도록 했습니다. 기존 신고에는 기본 지원 학교 ID를 읽을 때 연결하며 신고번호와 내용을 초기화하거나 삭제하지 않습니다.

운영진 전용 화면에서 신고 현황을 확인하고 처리 상태·담당자·처리 메모를 관리할 수 있습니다. 상태와 위험도별 요약, 검색·필터, 위험도 우선 정렬을 제공하며 현재 조건에 맞는 신고 목록을 CSV로 내려받을 수 있습니다.

### 학생 참여와 운영 기능

- **나도 겪었어요** — 같은 문제를 겪은 학생은 새로 신고하는 대신 기존 신고에 공감합니다. 기기마다 한 번만 세며, 운영진은 공감 많은 순으로 정렬할 수 있습니다.
- **처리 완료 후 만족도 확인** — 처리 완료된 내 신고에 "해결됐어요 / 아직 그대로예요"로 응답합니다. 미해결로 응답하면 신고가 다시 "확인 중"이 됩니다.
- **학교의 답변** — 운영진·교사가 신고한 학생에게만 보이는 답변을 남깁니다. 공개 "처리 결과"(처리 메모)와는 별개입니다.
- **처리 기한** — 긴급 1일·높음 3일·중간 7일·낮음 14일(분석 전 7일). 기한을 넘긴 신고는 운영진 화면에 빨간색으로 표시하고 "기한 초과"로 필터·정렬할 수 있습니다.
- **처리 이력** — 상태·담당자·학생 답변 변경, 안전성 검토, 만족도 응답을 누가(운영진/교사/신고자) 언제 했는지 기록합니다.
- **월별 통계와 보고서** — 월별 접수·완료율·평균 처리 시간·기한 초과 완료, 유형·위치·위험도별 접수, 최근 6개월 추이를 보여 주고 인쇄·PDF 보고서로 내보냅니다. 월 경계는 한국 시간 기준입니다.
- **학교 추가를 화면에서 처리** — 학교 신청 메일함에서 "승인하고 학교 등록"을 누르면 재배포 없이 학교 선택 화면에 바로 나타납니다. 위치는 기본 유형이 "확인 필요" 상태로 제공됩니다.
- **반복 신고자 걸러내기** — 학교는 학생 전체가 IP 하나를 쓰는 경우가 많아, 브라우저별 기기 토큰(서버에는 해시만 저장)으로 구분합니다. 10분 안에 3건 넘게, 하루 10건 넘게 보낸 기기의 신고와 운영진이 "장난 신고로 처리"한 기기의 신고(30일)는 **거부하지 않고 공개 전에 운영진 검토**를 거칩니다.
- **운영진 알림 (Discord 등)** — `NOTIFY_WEBHOOK_URL`로 Discord·Slack 등에 알립니다. 카카오톡·이메일은 Make·Zapier 같은 도구의 웹훅을 연결해 전달합니다.
  - 모든 신고(공개 보류 포함): 새 신고가 접수될 때마다 바로. **공개 보류 신고는 보류 사유·전체 내용·첨부 사진까지** 함께 보냅니다(사진 첨부는 Discord만). 보류 사진은 부적절할 수 있으니 운영진 전용 비공개 채널을 쓰세요.
  - 긴급 신고: 위험도가 기준(기본 "긴급") 이상인 신고. "모든 신고" 알림이 꺼져 있을 때와 접수 뒤 위험도 분석에서 늦게 긴급으로 판정됐을 때 보냄
  - 학교 신청 메일함: 새 학교 추가 신청이 들어오면 바로 (회신 이메일은 싣지 않음)
  - 월간 보고: 매달 1일 오전 9시 이후(한국 시간) 지난달 학교별 통계를 한 번. 서버가 잠들어 있었다면 깨어날 때 보냄
  - 운영진 화면 **"알림" 탭**에서 연결 상태 확인, 알림 종류 켜기/끄기, 테스트 알림, 원하는 달의 월간 보고 즉시 발송. "월별 통계" 탭에도 "디스코드로 보내기" 버튼이 있습니다.

### 위험도 분석

신고를 접수하면 서버가 AI에게 5개 요소를 각각 0~4점으로 채점하게 하고, **점수 계산과 등급 결정은 서버가** 합니다.

```
risk_score = (즉시성×30 + 사고가능성×30 + 피해정도×25 + 지속성×10 + 영향범위×5) / 4
             0~24 낮음 · 25~49 중간 · 50~74 높음 · 75~100 긴급
```

AI가 보낸 점수와 등급은 신뢰하지 않고 공식으로 다시 계산합니다. 덕분에 같은 신고를 여러 번 분석해도 결과가 흔들리지 않습니다. 즉각적인 안전 위험(전선 불꽃, 실제 화재, 구조물 낙하 임박 등)은 점수보다 우선해 긴급으로 올리되, "화재 대피 훈련" 같은 문맥은 구분합니다.

### AI 추가 질문

"학교가 별로예요" 처럼 담당자가 어디를 가서 무엇을 확인해야 할지 알 수 없는 신고는 그대로 저장해도 처리할 수 없습니다. 그래서 접수 전에 한 번 확인합니다.

```
신고 작성 → AI 확인 → 충분한가?
                       ├ 예   → 위험도 분석 → DB 저장
                       └ 아니오 → 질문 1개 → 답변 → 다시 확인 (최대 3회)
```

- **질문은 항상 하나**입니다. 여러 개가 오면 서버가 첫 질문만 남깁니다.
- 판단 기준은 "완벽한가"가 아니라 **"처리 가능한가"** 입니다. 장소와 문제만 알 수 있으면 날짜·시각·인원이 없어도 바로 접수됩니다.
- 대화 상태(최초 내용·질문·답변·직전 판단)는 서버 메모리 세션에 있고, **충분하다고 판단되기 전에는 DB에 저장하지 않습니다.**
- AI가 신고에 없는 사실을 만들어내면 서버가 걸러냅니다. 상세 위치는 학생 문장에 실제로 있는 표현일 때만 받아들이고, 학생이 쓰지 않은 숫자가 들어간 요약은 버립니다.

### 위치별 신고 현황

신고 폼은 선택 학교의 위치 유형 및 공식 위치 카탈로그를 사용합니다. 공식 목록에 없는 건물·층·교실·공간은 직접 입력할 수 있고, 직접 입력 값은 공식 위치로 승격되지 않습니다. 집계 시 학생이 적은 상세 정보를 함께 사용하며, 표기가 흔들려도 **확실할 때만** 같은 장소로 묶습니다.

```
"본관 3층 화장실" · "본관3층 화장실" · "3층 화장실"   → 본관 3층 화장실 (3건)
"본관 3층 화장실" · "별관 3층 화장실"                → 건물이 다르므로 분리
"3층 화장실" · "3층 남자화장실"                      → 같은 곳인지 알 수 없으므로 분리
```

건물 정보가 빠진 표기는 같은 층·같은 장소의 건물 지정 그룹이 **정확히 하나일 때만** 흡수합니다. 후보가 둘 이상이면 어느 쪽인지 알 수 없으므로 합치지 않습니다. 이 판정은 전부 문자열 규칙이라 **OpenAI를 호출하지 않으며**, 같은 데이터에 대해 항상 같은 결과가 나옵니다.

장소별로 총 건수, 가장 많은 카테고리, 높음 이상 위험도 건수, 최근 신고 날짜를 표시합니다. 모두 서버가 실제 DB에서 계산한 값이며, 해당하는 신고가 없으면 빈 그래프 대신 안내 문구를 보여줍니다.

### 내 신고는 어떻게 식별하나

로그인이 없으므로 신고 등록 시 서버가 추측 불가능한 토큰을 발급합니다. **브라우저에는 원본 토큰만, 서버 DB에는 SHA-256 해시만** 저장됩니다. 사용자 ID를 임의로 만들지 않습니다.

브라우저 저장소를 지우거나 다른 기기에서 접속하면 내 신고 목록은 비어 있습니다. 전체 신고에서는 계속 보입니다.

## 기술 구성

| 영역 | 사용 기술 |
|---|---|
| 프론트엔드 | React 19, TypeScript, Tailwind CSS 4, Vite 8 |
| 백엔드 | Express 4 (`server.ts`) |
| 저장소 | Supabase REST API (`schoolfix_store`) 또는 로컬 JSON 파일 |
| AI | OpenAI `gpt-5.6-terra` → `gpt-5.6-luna` 폴백, **서버에서만 호출** |
| 인증 | 없음 (삭제만 bcrypt 비밀번호 검증) |
| PDF / 인쇄 | 별도 라이브러리 없이 `@media print` + `window.print()` |

## 로컬에서 실행하기

**필요한 것:** Node.js 20 이상

```bash
npm install
npm run dev          # http://localhost:3000
```

`.env.local` 파일을 만들어 값을 채웁니다. (`.env.example` 참고)

```bash
OPENAI_API_KEY="sk-..."
ADMIN_PASSWORD_HASH="$2b$12$..."
STAFF_PASSWORD_HASH="$2b$12$..."
```

키가 없어도 **신고 등록·조회·검색·필터·PDF·인쇄는 그대로 동작합니다.** 위험도 분석과 AI 요약만 비활성화됩니다.

### 환경 변수

| 변수 | 필수 | 설명 |
|---|---|---|
| `OPENAI_API_KEY` | AI 기능 사용 시 | 위험도 분석 + AI 요약 |
| `ADMIN_PASSWORD_HASH` | 삭제 기능 사용 시 | bcrypt 해시. 없으면 삭제가 503 |
| `STAFF_PASSWORD_HASH` | 운영진 기능 사용 시 | 운영진 로그인용 bcrypt 해시. 없으면 로그인 기능 비활성화 |
| `SCHOOL_TEACHER_PASSWORD_HASHES` | 교사 로그인 사용 시 | 학교 ID별 비밀번호 bcrypt 해시를 담은 JSON 객체 |
| `NOTIFY_WEBHOOK_URL` | 선택 | 긴급 신고 알림을 받을 Discord·Slack 등 웹훅 주소 (HTTPS) |
| `NOTIFY_MIN_RISK` | 선택 | 알림 기준 위험도. `긴급`(기본)·`높음`·`중간`·`낮음` |
| `PUBLIC_BASE_URL` | 선택 | 알림 메시지에 붙일 사이트 주소 |
| `DATA_DIR` | 선택 | JSON 저장 경로. 영구 디스크용 |
| `ALLOWED_ORIGINS` | 선택 | 교차 출처 허용 도메인 |
| `PORT` | 선택 | 기본 3000. 호스팅이 자동 주입 |

관리자 비밀번호 해시 생성:

```bash
node -e "console.log(require('bcryptjs').hashSync('원하는비밀번호', 12))"
```

평문 비밀번호는 코드·번들·DB·로그 어디에도 저장하지 않습니다.

## API

## 보안

로그인이 없다는 것이 보안이 없다는 뜻은 아닙니다.

- **입력 검증** — 프론트엔드 검증을 신뢰하지 않고 서버가 최종 판단합니다. 허용된 위치·종류, 길이 제한, 첨부는 `data:image/*`만 허용.
- **부적절한 내용 보류** — 신고 텍스트와 첨부 이미지를 서버에서 OpenAI Moderation으로 검사합니다. 검토가 필요한 신고는 공개 목록·상세·통계에서 숨기고 운영진 검토 대기열에 보관하며, 운영진이 승인하거나 삭제할 수 있습니다. 검사 장애 시 이미지 첨부 신고는 자동 공개하지 않고 보류합니다.
- **욕설 필터** — 규칙 기반. 금지어 글자 사이 구분자를 허용하는 정규식으로 `씨 발`·`씨.발` 같은 우회를 잡되, 문장 전체 공백을 제거하지 않아 `보지 못했어요` 같은 정상 문장을 오탐하지 않습니다.
- **Rate Limit** — 신고 등록 / AI 요약 / 관리자 인증에 각각 적용. 학교는 NAT 뒤에서 IP를 공유하므로 신고 등록 한도는 여유 있게 잡았습니다.
- **Prompt Injection 방어** — 신고 내용은 `<report>` 안의 데이터로 고정되며, 그 안의 지시문은 실행하지 않습니다.
- **XSS** — React 기본 escape에 의존하며 `dangerouslySetInnerHTML`을 쓰지 않습니다.
- **보안 헤더** — CSP, X-Frame-Options, Referrer-Policy, HSTS(운영).
- **오류 비노출** — 사용자에게는 일반 메시지만, 상세는 서버 로그로.

## 배포

`render.yaml`이 포함되어 있어 Render에서 **New → Blueprint**로 저장소를 연결하면 구성됩니다. `OPENAI_API_KEY`, `ADMIN_PASSWORD_HASH`, `STAFF_PASSWORD_HASH`는 커밋하지 않고 대시보드에서 입력합니다. 운영진 로그인 비밀번호 해시는 다음 명령으로 생성합니다.

```bash
node -e "console.log(require('bcryptjs').hashSync('운영진비밀번호', 12))"
```

STAFF 비밀번호는 운영진 전체가 공유하는 단일 비밀번호입니다. 로그인 세션은 서버 메모리에 보관되며 8시간 뒤 만료됩니다. 서버가 재시작되면 기존 세션은 모두 로그아웃됩니다.

교사 비밀번호는 학교별로 별도 발급합니다. `schools.seed.json`의 학교 `id`를 키로 하는 JSON 객체에 bcrypt 해시를 등록하세요. 예: `{"cem-h":"$2b$12$..."}`. Render 환경 변수 `SCHOOL_TEACHER_PASSWORD_HASHES`에 등록하기 전까지 해당 학교 교사 로그인은 비활성화됩니다. 교사는 소속 학교 신고의 상태·담당자·처리 메모만 관리하며, 운영진 검토 대기열과 학교 신청 메일함은 이용할 수 없습니다.

배포 후 `https://<주소>/api/health`가 `{"status":"ok"}`를 반환하면 정상입니다.

### Supabase로 신고 데이터 영구 보관하기

Render 배포 흐름은 그대로 유지하고, 신고 및 학교 추가 신청 데이터만 Supabase에 저장할 수 있습니다.

1. Supabase에서 프로젝트를 만들고, **SQL Editor**에서 [`supabase/schema.sql`](./supabase/schema.sql)을 실행합니다.
   - **이미 Supabase를 쓰고 있었다면** 업데이트할 때마다 이 파일을 한 번 더 실행하세요. 화면에서 등록한 학교, 검토 대상 기기, 알림 설정을 저장할 수 있도록 테이블 제약을 갱신합니다. 실행하지 않아도 서버는 시작되지만 해당 기능의 저장이 "저장하지 못했습니다" 오류로 실패합니다.
2. Supabase 프로젝트의 **Project URL**과 서버 전용 Secret key(`sb_secret_...`)를 확인합니다. 이 키는 브라우저나 저장소에 절대 올리지 마세요. 구형 `service_role` JWT도 지원하지만 새 프로젝트에서는 Secret key를 권장합니다.
3. Render의 `schoolfix` 서비스 **Environment**에 `SUPABASE_URL`, `SUPABASE_SECRET_KEY`를 추가하고 저장합니다. `SUPABASE_SERVICE_ROLE_KEY`를 쓸 경우에는 `SUPABASE_SECRET_KEY`와 동시에 설정하지 마세요.
4. Render가 재배포된 뒤 `/api/health` 응답의 `dataStore`가 `supabase`인지 확인합니다.
5. 신고 사진은 신고 기록과 따로 **비공개 Storage 버킷**(`report-photos`, `SUPABASE_PHOTO_BUCKET`으로 변경 가능)에 저장됩니다. 서버가 시작할 때 버킷이 없으면 Secret key로 직접 만들므로 따로 할 일은 없습니다. `/api/health`의 `photos`가 `{ "store": "supabase", "ready": true }`이면 정상입니다. 버킷을 공개로 바꾸지 마세요. 공개 보류 신고의 사진은 서버가 운영진에게만 보여 줍니다.

두 환경변수는 반드시 함께 설정해야 합니다. 둘 중 하나만 있거나 테이블 접근에 실패하면 서버는 시작되지 않아 로컬 JSON 저장소로 조용히 되돌아가지 않습니다. Supabase 문서가 없을 때만 해당 종류의 로컬 JSON을 초기 가져옵니다. 이미 존재하는 문서는 자동으로 덮어쓰지 않으며, 문서 내용이 예상한 배열 형식이 아니면 서버가 시작을 거부해 잘못된 데이터 덮어쓰기를 막습니다. 배포 환경에 기존 JSON 파일이 없거나 별도 백업이 있다면 연결 전에 Supabase SQL Editor의 `schoolfix_store`에 가져오거나 운영자에게 데이터 이관을 요청해야 합니다.

**영구 저장 강제 안전장치:** Supabase 환경변수 설정 후 Render에 `REQUIRE_SUPABASE_STORE=true`를 추가하세요. 이 값이 켜져 있으면 Supabase 연결 설정이 빠진 배포는 시작되지 않습니다. 설정 전에는 `/api/health`가 `dataStore: "local-json"` 및 `persistence.durable: false`와 경고를 반환하므로 영구 저장 여부를 확인할 수 있습니다. Supabase 연결이 정상이라면 `dataStore: "supabase"`, `persistence.durable: true`가 표시됩니다.

### 무료 플랜을 쓸 때

- 15분간 요청이 없으면 잠들고, 다음 접속에 30~60초가 걸립니다.
- Supabase 환경변수를 설정하지 않으면 기존 JSON 파일 저장소를 쓰므로 재시작·재배포 시 데이터가 초기화될 수 있습니다.

데이터를 계속 보관하려면 위 안내에 따라 Supabase를 연결하거나 유료 플랜에서 영구 디스크를 붙이세요(`render.yaml` 주석 참고).

## 알려진 제한

- **실시간 알림 기능은 없습니다.** 새 신고가 접수되면 운영진이 화면을 새로고침해 확인해야 합니다.
- **Rate Limit이 인메모리**입니다. 인스턴스를 여러 개로 늘리면 Redis 같은 공유 저장소가 필요합니다.
- **욕설 필터는 모음 삽입 우회를 잡지 못합니다.** 모음을 구분자로 허용하면 정상 문장을 오탐하므로 의도적으로 제외했습니다.
- `data/` 폴더에는 신고 내용이 저장되며 git에 포함되지 않습니다.
